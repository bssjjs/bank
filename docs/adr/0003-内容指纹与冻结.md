# ADR 0003：内容指纹与冻结

- 状态：已采纳
- 日期：2026-11-22
- 相关：`docs/spec.md` 第 7 节、ADR 0001、ADR 0002、`src/bank/freeze.py`、`src/bank/repro.py`

## 背景

任务书 M2 要求两件事：

1. **内容指纹**：源文件指纹 + 两张表内容指纹（sha256），写 `FROZEN.json`，**两台机器重跑必须一致**。
2. **manifest**：一次构建的完整事实（行数、正例数、日期范围、列清单、配置指纹、构建器版本）。

同时演示线第一步要求「重跑指纹不变」。这就逼出两个问题：指纹到底算什么？冻结的边界在哪？

## 决策

### 1. 三级指纹，职责分开

| 指纹 | 算什么 | 用途 |
| --- | --- | --- |
| 源文件 `source.sha256` | `data/bank-marketing.db` 的字节 | 证明"原始数据没被换过"；上游换了库，这一项先变 |
| 配置 `config.sha256` | `configs/base.yaml` 解析后 `model_dump()` 的规范化 JSON | 证明"口径没被偷偷改"；改窗口/切点/名额比例，这一项变 |
| 内容 `tables.*.content_sha256` | 冻结后的 `train.parquet` / `valid.parquet` 的**规范化 CSV** 的字节 | 证明"两表内容一致"，跨机器可比 |

规范化 CSV 的规则写在 `repro.sha256_table()`：`to_csv(index=False, lineterminator="\n", float_format="%.10g", na_rep="")` 再 sha256。

**为什么不用 parquet 字节**：parquet 文件头里带写库版本、压缩实现细节，pyarrow 小版本升级就可能让同样数据产出不同字节。用 CSV 文本当"内容"的载体，只要列序、行序、浮点格式定死，两台机器就一致。

### 2. `FROZEN.json` 是"文件封条"，`manifest.json` 是"事实账单"

- `manifest.json`：给人看、给服务读的事实（窗口、行数、正例、列清单、清洗台账、容量、名额、口径版本）。**进 Git**。
- `FROZEN.json`：三份文件（两表 + manifest）的 sha256 封条 + 内容指纹。**进 Git**。
- 判据：**`--check` 以内容指纹为准**。parquet 字节变了但内容指纹一致 → 只警告（"换个 pyarrow 版本重写了一遍，内容没变"）；内容指纹变了 → 失败（"数据集真的变了，先解释再继续"）。

### 3. 冻结的边界

- 冻结的输入：只读入口 `raw.connect()`（`mode=ro` + `PRAGMA query_only=ON`）+ `configs/base.yaml`。
- 冻结的产物：`data/frozen/{train.parquet, valid.parquet, manifest.json, FROZEN.json}`。
- **清洗不删行**：所有行数变化只能来自窗口裁剪，`manifest` 的 `window` 段记录起止日期，`cleaning` 段记录每条规则的命中行数与致命/记账标记。
- 冻结是一次性的：训练、评估、服务都只读 `data/frozen/`，不碰原始库，也不在内存里"顺便"重新算一遍口径。

### 4. 确定性从哪来

- 行序：`SELECT rowid AS "序号", *` 显式带序号，绝不依赖 `SELECT *` 的返回顺序（踩坑清单第 8 条）。
- 时间轴：由序号 + 月份 + 日号重建，规则在 `timeaxis.py`，异常月份/日号回退直接抛错。
- 配置指纹：`canonical_json` 用 `sort_keys=True`、`ensure_ascii=False`、`separators=(",", ":")`、路径转 `as_posix`、日期转 `isoformat`，未知类型抛 `TypeError`——不做"尽力而为"的序列化。
- 名额：`ceil(3556 × 0.10) = 356`，浮点先 `round(..., 9)` 再取整，避免 `355.60000000000002` 这种边界抖动。

## 否决的方案

| 方案 | 为什么不选 |
| --- | --- |
| 只算 parquet 字节 sha256 | pyarrow 版本一变就"数据变了"，实际内容没变，团队会被假警报拖住 |
| 只算行数 + 正例数 | 太粗，改一个特征值发现不了 |
| 把 `data/frozen/` 也挡在 Git 外，靠命令现场重建 | 演示现场重建要 3 秒还行，但"两台机器一致"就无法取证；任务书明确要求冻结集可交付 |
| 每次训练都重新从原始库构建 | 训练与服务会各算一套口径，迟早对不上（参考项目 diabetes-v0 的病灶） |

## 后果

- 好：任何人 `python -m bank.freeze --check` 就能判断"我手上的数据是不是那一批"，答辩时可以直接演示。
- 好：`tests/test_freeze.py` 把 `manifest` 的数字钉死了（21,093/4,109、17,537/2,327、3,556/1,782、名额 356），谁改了口径测试先红。
- 代价：改口径要重建 + 重跑测试 + 提交新的 `FROZEN.json`，多一步。这是故意的——口径变更本来就该有痕迹。
- 代价：内容指纹依赖 `to_csv` 的格式约定，将来若要换指纹算法，必须新旧并存一轮并在 ADR 里记录。
