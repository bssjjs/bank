# ADR 0018：告警渠道与定时检查（F6）

- 日期：2026-11-24
- 状态：已采纳
- 关联：ADR 0008（漂移阈值与三条重训条件）、ADR 0014（预测记录 v2 与回流）、ADR 0015（服务指标）

## 背景

到 `drill`（F7）为止，能回答的是「注入的漂移，监控看得见吗」。
但演示线第 7 步跑完 `bank_training.drift` 就没人管了：PSI 变红之后谁被打扰？
讲义 F6 的要求是「变差了谁第一个知道」——要有告警渠道，还要有定时任务，
否则监控只是一份需要人主动去读的报告，不是监控。

## 决定

1. **检查逻辑一处、投递渠道可换。** `watch.py` 只负责「算出这批告警」，
   `bank/alerts.py` 只管「把一批告警送出去」。渠道三选：`console`（终端）、
   `file`（JSONL 追加）、`webhook`（POST JSON，超时 3 秒）。
2. **一次检查只发一批，不是一条一发。** 一次跑完收集所有告警，最后统一投递。
   理由：一轮检查里 6 个特征越线是常态，逐条推送会把人训练成"忽略告警"。
3. **渠道失败降级为告警，不让监控崩。** `webhook` 连不上时返回一条
   `channel/webhook_failed`（warn），本轮其他告警照常落盘。理由：告警发不出去
   这件事本身就该被知道，而监控进程崩掉会更难发现。
4. **服务不可达是 warn，不是异常。** 定时任务不该因为 API 没起就整轮失败；
   但「这轮看不见线上状态」必须写进报告。
5. **重训建议要「连续两次」。** 只按 ADR 0008 第一条：同一特征 PSI≥0.25
   **连续两次检查**都超，才报 `retrain/psi_two_runs`；历史写在
   `data/processed/watch_history.jsonl`（每轮一行，只记 `breaches`）。
   单次越线仍然报 `alert`，但不直接跳到「建议重训」——这一步留给人的判断。
6. **阈值进 `configs/watch.yaml`，强校验。** 关注线 0.1、告警线 0.25、
   认购率变化 50%、覆盖率下限 0.7；`psi_alert` 必须大于 `psi_watch`，
   渠道字段按 kind 校验（file 必须有 path、webhook 必须以 http 开头）。
7. **退出码 1 表示有 alert 级告警。** 这样 `watch --no-send` 可以直接放进
   流水线当判定，而不只是给人看。

## 没有选的做法

- **不做常驻守护进程。** `--interval` 只用来演示「每小时看一眼」，真正的调度
  交给外部 cron / 任务计划程序；我们没有进程管理基础设施，写一个半吊子的
  守护进程只会多一个需要监控的东西。
- **不做 Prometheus 导出。** 服务指标走 `/metrics` 的 JSON（ADR 0015），
  告警走 JSONL / webhook；引入 Prometheus 就要多一套运维，本项目没有。
- **不在告警里带客户特征值。** 告警只写特征名、PSI、比例；`/metrics` 与
  预测记录都不写特征值（ADR 0014/0015），告警不能成为泄露口。
- **不自动重训、不自动改 `configs/model.yaml`。** 重训是有人负责的动作，
  条件到了只报警，命令留给人跑（ADR 0016 同样的立场）。

## 后果

- 演示可以现场造一次漂移（`drill`）→ 跑 `watch` 看到对应告警 → 再跑一次
  看到 `psi_two_runs`；这条链不依赖任何外部服务。
- 新增文件：`configs/watch.yaml`、`packages/core/src/bank/alerts.py`、
  `packages/training/src/bank_training/watch.py`、`tests/unit/test_watch.py`（17 项）。
- 预测记录、回流、告警三处都只写"事实"，不写客户特征值。
- 告警的阈值是**报告口径**，不是准入门槛；改阈值不需要重跑冻结或训练。
