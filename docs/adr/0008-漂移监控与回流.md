# ADR 0008：漂移监控与回流

- 日期：2026-11-22
- 状态：已采纳（M7）
- 相关：ADR 0003（内容指纹与冻结）、ADR 0006（模型包与发布）、`packages/core/src/bank/drift.py`、`packages/training/src/bank_training/drift.py`

## 1. 背景

任务书 M7 要求两件事：

- **必须实现**：对"线上"数据跑漂移，至少一个特征给出 PSI。
- **必须设计**：标签回流、对照组、重训条件。

这个数据集没有真实线上流量，所以"线上"只能用**验证期数据**扮演：它的时间在训练之后
（`≥ 2009-10-01`），正例率 50.11% 对训练期 13.27%，本身就是一次真实的分布平移。
这不是造假——它是"用历史数据回放一次监控"，答辩时要说清演的是哪一段。

## 2. 决定

### 2.1 PSI 只看 15 个原始输入 + 分数

模型包里的 21 个特征里，有一半是派生列（`距上次联系天数_log` / `档`、`是否被联系过`、
`教育程度序`、`月份连号` 等）。派生列由原始列唯一决定，再报一遍会让台账出现
"两个特征同时漂移"的假象。所以监控口径是：

- 15 个 `bundle.doc.inputs`（用户填的原始业务列）各算一个 PSI；
- `score` 单独一项：同一个模型喂两个时期的特征，看分数分布有没有整体平移；
- 正例率单独一项，用相对变化（%）表示。

### 2.2 分箱边界只从基准集取

数值列：等频 10 箱，边界用**基准集**（冻结的 `train.parquet`）的分位数算，
线上批次沿用同一组边界。这是 PSI 的标准做法，也是唯一能发现"整体平移"的做法——
两边各算各的分位数，分布再变，比例都差不多。

缺失单独占一箱，不与任何区间合并；基准集整列全空时直接报错（这说明口径本身坏了）。

类别列：按取值分布算；基准集没见过的取值合并成"其他"（记 `unseen_share`）。
否则线上冒出一个新职业，会变成"10 个箱全归零"，PSI 爆表但看不出原因。

### 2.3 阈值与落盘

- 阈值：PSI < 0.1 稳定、0.1–0.25 关注、> 0.25 严重（教科书口径）。
- 结果写 `data/processed/drift.json`（契约名 `drift_report.v1`），含每个特征的
  箱边界、每行两个时期的行数、基准集内容指纹前 16 位。
- 同时记一个 mlflow run `m7-drift`：`psi_<特征>` 与 `psi_score`、两个时期的正例率。

### 2.4 回流与重训（设计，未接真实流量）

**标签回流**：`POST /v1/predict` 的返回里有 `request_id`，每条预测另起一行写进
`data/processed/predictions.jsonl`（含 `control` 标记）。外呼结束后，把"这个 request_id
最终有没有认购"追加进 `data/processed/labels.jsonl`（`request_id, label, labeled_at`），
按 request_id 与预测记录 join，就得到"这批外呼的真实结果"。7 天内没回填的按未认购处理
并单独标记 `censored`，不混进精确率。

**对照组**：预测接口支持 `?control=true`，调用方按 10% 的比例**随机**抽一部分请求打这个标记
（与分数无关）。对照组的作用是估计"不按模型排序、凭名单硬打"的转化率，
用来回答答辩必问的"模型到底有没有用"。对照组数据**不进重训**，只做评估——
按分数之外的方式抽样会把选择偏差带回训练集。

**重训条件**（三条，命中任一条就重训，不靠拍脑袋）：

1. 任一原始输入的 PSI ≥ 0.25，且连续两个统计周期（按月）都超；
2. 用回流标签算的名额内精确率，比 `docs/model_card.md` 记录低 5 个百分点以上；
3. 正例率相对变化超 ±50%。

**重训流程**：滚动窗口重跑 `bank.freeze`（配置指纹会变，内容指纹也要重算）→
`bank_training.train` → `bank_training.export --version <新版本>`（门禁 AP ≥ 0.50、
名额内精确率 ≥ 0.60）→ 改 `models/serving/current.json` 指向新版本。旧版本目录不删，
回退就是把指针改回去。

## 3. 这次回放看到什么

`python -m bank_training.drift`（基准 = 训练期 17,537 行，对照 = 验证期 3,556 行）：

| 特征 | 类型 | PSI | 判定 |
| --- | --- | --- | --- |
| 联系月份 | 类目 | 3.4028 | 严重 |
| 住房贷款 | 类目 | 0.8087 | 严重 |
| 上次营销结果 | 类目 | 0.6573 | 严重 |
| 职业 | 类目 | 0.4583 | 严重 |
| 历史联系次数 | 数值 | 0.3500 | 严重 |
| 年龄 | 数值 | 0.2797 | 严重 |
| 联系方式 | 类目 | 0.2318 | 关注 |
| 联系日期 | 数值 | 0.2003 | 关注 |
| 账户余额 | 数值 | 0.1944 | 关注 |
| 距上次联系天数 | 数值 | 0.1604 | 关注 |
| 个人贷款 / 教育程度 / 是否信贷违约 / 本次联系次数 / 婚姻状态 | — | ≤ 0.0881 | 稳定 |
| score | 分数 | 1.0851 | 严重 |

正例率：13.27% → 50.11%（+277.66%）。

**怎么读这张表**（答辩要能解释，别把它当事故）：

- `联系月份` PSI 3.40 是"跨年"造成的：训练期只有 2008-11 至 2009-09 的月份，
  验证期出现 10 月，而 10 月在基准集里一个样本都没有。这是**日历漂移**，
  不是数据错误。同理 `上次营销结果` 从"几乎全是未知"变成"多数已知"——
  2009 年下半年起营销活动开始复用历史客户。
- `距上次联系天数` 0.16 是哨兵占比变化的体现（从未联系 100% → 34%），
  派生三列已经把这件事表达清楚了，所以这里不重复报派生列。
- `score` 1.09 与正例率 +277% 同向：不是模型坏了，是**这一期的人本来就更愿意买**。
  这也解释了为什么验证集上 Brier 0.2852、平均分 0.2719 远低于基率 0.5011。

## 4. 否掉的方案

| 方案 | 否掉的理由 |
| --- | --- |
| 两边各自算分位数 | 自适应分箱会把平移抹平，PSI 永远接近 0，等于没监控 |
| 缺失并进第一箱 | 缺失往往就是上游改了采集口径，必须单独可见 |
| 21 个特征全报 | 派生列与原始列重复，台账里会出现"两个来源"的假象 |
| 只看 score 漂移 | 知道"变了"，不知道"哪一列变了"，没法定位 |
| 把 PSI 阈值写死成报警 | 0.1 在类别列上噪声很大；本项目的用法是"按月看趋势 + 三条重训条件" |
| 对照组按分数抽样 | 会引入选择偏差，回流数据不能直接进重训 |

## 5. 后果

- 监控只看 15 个输入列，加字段时 `bundle.doc.inputs` 自动带上，不用改监控代码。
- `drift.json` 里带基准集指纹：换冻结集后旧报告自动失效（指纹对不上）。
- 真接线上流量时，只需把 `--current` 指向导出的批次 parquet；
  预测记录与 `labels.jsonl` 的 join 是下一步的工程活，本课程范围内只做到设计。
