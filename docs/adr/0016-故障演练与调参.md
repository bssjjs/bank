# ADR 0016：故障演练与调参都只在训练期里做

- 日期：2026-11-24
- 状态：采纳
- 相关：ADR 0002（时间切分）、ADR 0008（漂移监控与回流）、ADR 0011（评估报全）、ADR 0005（模型选择）

## 背景

两条命令都是"证明某件东西真的会动"的工具，但都能变成作弊入口：

1. **监控要能证伪。** 只看到"验证期 PSI 很高"不能说明监控有用——也可能是分箱方式本身就会报红。
   真正要证明的是：**已知的、人为制造的漂移，监控必须抓到；没被制造变化的列，监控必须不响。**
   如果一次都不演练，监控坏了也看不出来（它平时只在后台写 JSON）。
2. **调参要能不偷看。** 拿验证集挑超参数是最常见的隐性作弊：换来的分数不是"没见过数据"的成绩。
   讲义要求调参只用训练期里再切出来的一段，而且切分本身要能失败。

## 决定

### F7 演练：注入已知漂移，看监控响不响

`python -m bank_training.drift` 只在后台写 `drift.json`，不会证明它有用。新增
`python -m bank_training.drill`（`packages/training/src/bank_training/drill.py`），
在验证集副本上做四种注入，再断言五项结果（其余列原样）：

| 检查 | 注入 | 期望 |
| --- | --- | --- |
| 数值漂移被抓到 | `账户余额 × 1.5 + 5000` | PSI ≥ 0.25（严重） |
| 类别漂移被抓到 | `职业` 随机一半改「未知」 | PSI ≥ 0.25 |
| 标签漂移被抓到 | 六成负例翻正例 | 正例率相对变化 ≥ 50% |
| 没动的列不许乱响 | `婚姻状态` 原样 | PSI < 0.1（稳定） |
| 反证：自适应分箱会看不见 | 同一份 `账户余额`，两边各算分位数 | PSI < 0.1 |

最后一条是给 ADR 0008 做实验证据：如果按两边各自的分位数分箱，人为平移"看起来"就不漂了——
所以监控必须用基准集的固定边界。注入用固定种子（`DRILL_SEED = 20261122`），同一台机器两次跑结果一致。

实测（2026-11-24，`python -m bank_training.drill`）：数值 **12.4432**、类别 **3.1173**、
标签 0.5011 → 0.8003（**+59.7%**）、对照 **0.0084**、反证 **0.0233**，五项全响。
mlflow run `5dff841cf54c41d99af5f68651fdb02c`，JSON 写 `data/processed/drill.json`。

### C-L3b 调参：验证集一次都不读

`python -m bank_training.tune` 把训练期（`< 2009-10-01`，17,537 行）再切：

- 拟合段 `< 2009-04-01`：7,341 行（2008-11-04 ~ 2009-03-31）
- 内层评估段 `[2009-04-01, 2009-10-01)`：10,196 行（2009-04-01 ~ 2009-09-30）

网格 `C ∈ {0.3, 1, 3, 10}`，每格一个 mlflow run（`c-l3b-tune-c<c>`），按内层 AP 选中。
`inner_split()` 里断言评估段最后一天**早于** `split.cut`——验证集漏进来会直接抛错，不靠自觉。

实测（内层评估段，名额 = 10,196 × 10% = 1,020 人）：

| C | AP | ROC-AUC | 名额内精确率 |
| --- | --- | --- | --- |
| 0.3 | 0.2647 | 0.6370 | 0.3324 |
| 1.0 | 0.2720 | 0.6405 | 0.3490 |
| 3.0 | 0.2735 | 0.6410 | 0.3529 |
| 10.0 | **0.2741** | 0.6412 | **0.3549** |

最高与最低只差 **0.0094**，落在我预设的噪声线 0.01 以内。结论：**这组数据上调 C 不值得**，
`configs/model.yaml` 保持 `c: 1.0` 不动；命令只打印推荐值，不写配置。

## 为什么推荐值不自动写进配置

调参命令如果自己改 `configs/model.yaml`，会同时改掉「模型选择」这个已经被 ADR 记录的决定，
而新的数字要重跑 `train` → `export` → 刷新 `baselines/` 才自洽。这类改动应该是人看完整张表之后
自己动手，并且在提交信息里说明依据。机器只负责把证据摆出来。

## 否掉的方案

- **不演练，只讲"监控会告警"**：告警阈值同样是代码，没演练过就不知道它是坏的还是没触发。
- **用线上真实漂移当演练**：只有一次机会，且没有"已知答案"，证明不了监控的灵敏度。
- **注入时用 `random.shuffle` 不设种子**：结果不可复现，测试无法断言。
- **调参直接拿验证集做**：任务书一票否决项（用验证集调参选模型）。
- **调参自动重写 `model.yaml`**：绕过"改模型要有 ADR + 重跑全链"的纪律。
- **按 `spread` 自动切到 AP 最高的 C**：0.0094 的差在 1,020 人的名额内是几十个人的噪声，
  自动切换等于用噪声改决定。

## 后果

- 质量门多跑两个测试文件；`pytest tests` 从 292 增到 305。
- 演示时多两条命令，都能在 30 秒内出结果，且输出"响/没响"这种一眼能看懂的行。
- 调参结论写在这里，`configs/model.yaml` 不改；哪天真的要换 `C`，先改这份 ADR 再重跑全链。
