# ADR 0013：注册表、门禁与审计

- 状态：已采纳（2026-11-24）
- 相关：`packages/core/src/bank/registry.py`、`packages/training/src/bank_training/export.py`、ADR 0006（模型包与发布）、ADR 0008（漂移与回流）

## 背景

M4 做出模型包以后，"哪个版本在线"只有一个 `current.json` 指针；"这个版本是谁、凭什么上去的、什么时候改的"全在人的记忆里。讲义 D-L2 的要求是：门禁（能不能上线）→ 注册表与别名（谁在线）→ 发布晋升（怎么换），并且 D-L3 要求"先有记录，再改状态"。

原来的 `export.py` 写完包就顺手把 `current.json` 改成新版本，等于**导出即上线**：门禁再怎么严也只是打印一行字，不能真的拦住。

## 决定

`models/serving/` 下三份文件分工（都不进 Git）：

| 文件 | 内容 | 谁写 |
| --- | --- | --- |
| `registry.json` | 每个版本的状态、门禁结果、指标、run_id、checksum、别名 | `registry.py` |
| `audit.jsonl` | 只追加的事件流（register / stage / promote / rollback / retire） | `registry.py`，先写它再改状态 |
| `current.json` | 线上指针，服务只读它 | 只有状态真的变成 `production` 时才写 |

### 1. 四个状态与迁移表

```
candidate --stage--> staging --promote--> production --retire--> retired
                       ^   |                  |                      |
                       |   +--retire--> retired|                      |
                       +-------rollback--------+<----stage------------+
```

代码里就是 `TRANSITIONS = {"candidate": {"staging"}, "staging": {"production", "retired"},
"production": {"staging", "retired"}, "retired": {"staging"}}`。不在表里的迁移直接抛 `RegistryError`，不做"差不多就放行"。

### 2. 门禁先行

`promote` 的第一步是 `_require_gate()`：门禁没过，一步都不动——状态不变、`audit.jsonl` 不多一行。这是踩出来的：第一版先自动 `stage` 再查门禁，失败的发布会在审计里留下一条"stage"却没留下"为什么没上去"，事后查不清。同理 `rollback` 也查门禁（回退到一个没过门禁的版本等于把上一轮的问题带回来）。

门禁本身仍然写在 `export.py` 的 `_gate()`（AP ≥ 0.50、名额内精确率 ≥ 0.60、特征数 ≥ 10、ROC-AUC > 0.5）；注册表只**存**结果（`GateRecord(passed, checks)`），不重算指标——重算就得再读一遍冻结集，那是训练层的事。

### 3. 审计先行

`_record()` 追加一行 JSON 之后 `flush()` + `os.fsync()`，然后才 `_save(registry.json)`。顺序反过来的话，进程在两次写之间崩掉就会出现"状态变了但没人知道为什么"。`events()` 解析时坏行连行号一起报。

### 4. 别名与回退

`aliases["production"]` 指向当前线上版本；`rollback(version)` 只改指针、把原线上版本降成 `staging`（不删目录、不改包内文件）。这样回退是**一次指针写入**，不是重训或重打包——M4 的"不覆盖旧版本"在运行时也要成立。

`export.py` 默认只 `register`（状态 `candidate`），不再碰 `current.json`；要上线得显式 `--promote` 或 `python -m bank.registry promote <版本> --reason "..."`。`tests/support.py` 与 `scripts/replay_steps.py` 都加了 `--promote`，否则干净检出里没有线上版本，服务测试会 503。

### 5. 封存集：设计好了，这轮没开箱

D-L3 要求"封存集只开一次"。我们的数据是 21,093 行（训练 17,537 / 验证 3,556），验证集已经是最后一段时期（2009-10 ~ 2010-11，正例率 50%）。再切一段封存集会把验证集切碎（3,556 → 2,000 多），而名额 356 人、名额内精确率的 95% 区间宽度约 ±4pp，切碎以后区间宽到没有判断力。

所以这一轮：**封存集的规则写进文档、代码里不留开箱入口**——`ADR 0002` 写明"暂不切封存集"，`architecture.md` §7 写明"没做：封存集"。要做的话，前提是先有更多数据（例如按天回流的真实预测），不是从这 3,556 行里再切一块。

## 否掉的方案

- **只留 `current.json`**：说不清"为什么是这个版本""曾经上线过什么""谁改的"。
- **把状态写进 `bundle.json`**：模型包是只读产物，状态是运行期事实；改包内文件会破坏 checksum。
- **用 SQLite 存注册表**：一份 JSON 就够，还能直接 `git diff`/人工读；SQLite 又会引入一个新的并发写问题。
- **发布时删旧版本目录**：回退就没了，且违反"不覆盖旧版本"。
- **回退 = 改 `current.json` 手写**：绕过门禁与审计，等于没有状态机。

## 后果

- 上线变成两步（导出 → 发布），多一条命令，换来"谁在线上、凭什么"可查。演示时可以现场 `export` 一个新版本（停在 candidate）、`promote`、`rollback`，审计事件一条条长出来。
- 审计是唯一事实来源：`registry.json` 与 `audit.jsonl` 不一致时以审计为准（当前实现是同一次调用里先写审计，因此不会出现）。
- `models/serving/registry.json` 里的指标是导出那一刻的快照，和 `bundle.json` 的 `metrics` 同源；不要手改。
- 测试从 250 项增至 260 项（`tests/unit/test_registry.py` 10 项）。
- 演练实测：先 `export --version 1.1.0`（candidate）→ `promote`（production，1.0.0 降 staging）→ `rollback 1.0.0`（production，1.1.0 降 staging），共 7 条审计事件。
