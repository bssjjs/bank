## 3. 为什么行数比 UCI 的 41,188 多

UCI 页面上的 `bank-additional-full.csv` 是 41,188 行，本机库是 45,211 行。差异来自去重口径：完整版做过"同一客户在本次活动中重复联系"的合并，而本库保留了每次联系尝试（这也是为什么没有客户 ID 可用）。**本项目的建模单位是"一次联系尝试"**，所以保留下全部 45,211 行；这件事写在这里，避免答辩时被问住。

> 复核方式：UCI 页面 `bank-additional.zip` 里的 `bank-additional-full.csv` 行数 41,188；本机库 `SELECT COUNT(*)` = 45,211。如果老师要求与 UCI 严格一致，需要重新导入并重跑全部口径——代价是重做 M2 与 M3，所以必须以 ADR 记录这个选择（ADR 0001）。

## 4. 时间轴：行序就是时间序

原始表**没有年份列**，只有 `联系月份`（中文）与 `联系日期`（月内第几天）。项目早期文档（`notebooks/数据口径说明.md` §2.5）据此认为"无法按时间切分，只能随机切分"。**这个结论是错的**，证据如下（全部可复现）：

1. 按 `rowid` 顺序，`联系月份` 形成 **30 个月块**，从 2008-05 连续走到 2010-11；月序只发生两次"十二月 → 一月"的回绕（2008→2009、2009→2010），没有其它回退。
2. 每个月份块内部，`联系日期`（日号）**从不回退**：块内单调不减。
3. 按「起始 2008-05 + 月份顺序 + 日号」重建出 **561 个不同日期**，全局单调递增，范围 2008-05-05 → 2010-11-17。
4. 重建日期与 UCI `bank-additional` 文档中"按日期排序"的描述一致。

因此：**按时间切分是可行的，而且必须这么做**（随机切分会把同一时期的样本同时放进训练与验证，验证集不再"像未来"）。实现见 `src/bank/timeaxis.py`，读取时必须 `SELECT rowid AS 序号`——不能依赖 `SELECT *` 的返回顺序，也不能在中间环节重排。

## 5. 标签分布随时间剧烈漂移（最重要的一条）

| 时期 | 行数 | 正例 | 正例率 | 本次联系次数均值 | 从未联系占比 | 上次结果已知占比 |
| --- | --- | --- | --- | --- | --- | --- |
| 2008H1 | 12,443 | 459 | 3.69% | 2.845 | 100.0% | 0.0% |
| 2008H2 | 15,286 | 942 | 6.16% | 3.464 | 94.0% | 6.0% |
| 2009H1 | 12,665 | 1,643 | 12.97% | 2.190 | 63.8% | 36.2% |
| 2009H2 | 2,197 | 893 | 40.65% | 1.785 | 53.2% | 46.6% |
| 2010H1 | 1,460 | 777 | 53.22% | 1.874 | 34.2% | 65.8% |
| 2010H2 | 1,160 | 575 | 49.57% | 1.899 | 34.4% | 65.5% |

这组数字的含义：

- 早期（2008）是"广撒网"：名单全量外呼、几乎没人被联系过、上次结果全是未知，认购率 3.7%。
- 后期（2010）是"精准打"：只联系以前联系过的人、每人被打多次，认购率升到 50% 左右。
- **这不是数据错误，是营销策略本身在变**。它直接决定三件事：① 必须按时间切分；② 验证集基率 50%、训练集 13%，模型概率会系统性偏低，Brier 会很难看，报告时必须说明是漂移；③ 特征的重要性也会随时间变（`距上次联系天数` 在 2008 全是 −1，在 2010 才有信息）。

## 6. 哨兵值、未知值与口径冲突

| 项 | 数值 | 说明 |
| --- | --- | --- |
| `距上次联系天数 = −1`（从未联系） | 36,954（81.74%） | 哨兵，不是天数；拆成 3 列 |
| `距上次联系天数 ≠ −1`（联系过） | 8,257 | |
| `上次营销结果 = 未知` | 36,959（81.75%） | 类别，不是缺失 |
| `职业 = 未知` | 288 | 类别 |
| `教育程度 = 未知` | 1,857 | 类别 |
| `联系方式 = 未知` | 13,020（28.80%） | 类别，认购率全表最低一档 |
| **口径冲突**：`距上次联系天数 ≠ −1` 但 `上次营销结果 = 未知` | **5 行** | 逻辑上"联系过"就该有上次结果。保留原值、登记台账、不修改；M2 的清洗规则里明确写出 |

`联系方式` 的三种取值：手机 29,285、固话 2,906、未知 13,020。未知占比接近三成，且与认购率强相关，所以"未知"绝不能填众数——填了就等于把最难触达的人群改造成普通人。

## 7. 泄漏列的证据

`通话时长`：均值 258.16 秒，中位数 180 秒，P95 751 秒，最大 4,918 秒。

**只用这一列做单变量排序，ROC-AUC = 0.8076。** 一列就接近"完整模型"的水平，这不是因为它有用，而是因为它是通话的结果：聊得久的人往往有兴趣。预测时点（通话前）拿不到它，所以禁用；E1 实验（`spec.md` 第 6 节）会把它加回去做反证，预期指标大幅虚高。

## 9. 已知缺陷与使用限制

1. **没有客户 ID**：同一客户多次联系无法识别，不能按人分组切分，也不能去重；模型学的是"这次联系值不值得打"。
2. **没有年份列**：年份靠行序重建，一旦有人重排原始表，时间轴立刻失效（`timeaxis.py` 会报错而不是猜）。
3. **2008-09 整月缺失**：无法区分是活动暂停还是数据丢失。
4. **标签只有"打过的人"**：没打过的人没有标签，模型无法评估"没打的人里有多少会买"，这是所有历史数据的通病，写进模型卡的适用范围。
5. **时期漂移剧烈**：模型效果会随时间衰减，必须靠 PSI 监控（M7）与重训条件来管，不能训一次用三年。
6. **准标识字段**：年龄、职业、教育、婚姻可间接识别小群体，禁止用于个体决策与对外披露。
7. **尚未冻结**：`data/frozen/FROZEN.json` 与内容指纹在 M2 生成；在那之前"同一份数据"只靠本机这一个文件保证。
