# 问题定义与口径（M1）

> 本文件回答任务书的 M1「必须实现」：一句话定义、口径规格表（见 `spec.md`）、禁用列清单（见 `spec.md` 第 3 节）、数据卡（见 `data_card.md`）、朴素版与规范版对照（见 `spec.md` 第 6 节，数字由 M3 回填）、踩坑清单（见 `pitfalls.md`）；以及「必须设计」：成功标准与非目标。

## 1. 业务背景

银行电话营销团队每天有固定外呼名额（坐席数 × 工作时长），名单里的人只能打一部分。名单本身不区分优先级，随机打的结果是：绝大多数通话没有结果，坐席时间被浪费在几乎不可能认购的人身上。

我们能改变的不是"客户会不会买"，而是"今天先打给谁"。所以这是一个**排序问题**，不是"预测谁会买"的学术问题：模型输出的分数只需要在当天的人里排出先后，决策动作是"把有限的名额分配给分数最高的人"。

## 2. 一句话定义

> **在每次外呼之前（通话发起前一刻）**，用**那时系统里已有的客户属性与历史联系记录**预测**本次被拨打的客户**在**本次通话结束时**会不会**认购定期存款**，按**每天外呼名额（当天分数前 10%）**决定**今天先打给谁**。

逐项对应任务书模板：

| 模板要素 | 本项目的取值 | 为什么是这个 |
| --- | --- | --- |
| 预测时点 | 通话发起前 | 打电话之后才知道的信息（通话时长、本次结果）都不能进特征 |
| 那时能拿到的信息 | 客户属性、贷款与违约状态、账户余额、历史联系记录（次数、上次结果、距上次联系天数）、联系日期与月份 | 见 `spec.md` 第 1 节逐列判定 |
| 预测对象 | 本次被联系的客户（一行 = 一次联系尝试） | 数据没有客户 ID，无法按人聚合，只能按"联系尝试"建模 |
| 时间窗口 | **0 天**：标签在本次通话结束时立即产生 | 业务动作是"这次打不打得到"，不是"未来 90 天内会不会买"，因此不存在观察窗口与成熟期 |
| 事件 | 是否认购定期存款（`是否认购 = 是`） | 原始表的唯一结果列 |
| 决策动作 | 按分数排序，取当天名额内的人优先外呼；名额 = 验证集行数 × 10% | 名额是业务给的外生约束，不是模型学的阈值 |

「时间窗口为什么这么长」这个答辩必问题的答案：**它不长，是 0**。标签在通话结束的瞬间就确定了，没有滞后回填，所以既不需要 30/90 天的观察期，也不需要"成熟期"等待。代价是：标签只覆盖"已经打过的人"，没打过的人没有标签——这也是为什么必须按时间切分（见 `spec.md` 第 4 节）。

## 3. 标签与决策口径（摘要，细节见 `spec.md`）

- 标签：`label = 1` 当且仅当 `是否认购 = "是"`；缺失或其它取值一律报错，不静默当负例。
- 基率：全表 5,289 / 45,211 = 11.70%；但按时间切分后，验证期（2009-10~2010-11）基率是 **50.11%**——这是宏观环境与名单策略变化造成的，不是数据错误（见 `data_card.md` 第 5 节）。
- 名额：验证集 3,556 行 × 10% = 355.6 → **356 人**。名额人数由「验证集行数 × 配置比例」算出并在训练时打印，不允许写死。
- 阈值 0.5 同时计算并记录，但**不作为验收口径**：基率 50% 时阈值 0.5 近似"全员入选"，没有业务意义。

## 4. 成功标准

### 4.1 能演示（硬性）

任务书演示线八步必须现场走通；其中与本文件相关的一步是：一条命令从原始数据生成训练集/验证集，打印行数、正例数、内容指纹，重跑指纹不变。

### 4.2 指标门槛（可验收）

在**验证集**（2009-10-01 ~ 2010-11-17，3,556 行，1,782 正例，基率 50.11%）上、**名额 356 人**的口径下：

| 指标 | 门槛 | 为什么要它 |
| --- | --- | --- |
| 名额内精确率 | ≥ 75%（356 人里 ≥ 267 人认购）；实测 74.16%，差 0.84pp，未达 | 直接对应坐席产出；低于此模型不如随机名单 + 人工筛选 |
| 名额内召回率 | 只报告，不设门槛；实测 14.81% | 原写 ≥30% 与名额 356 不相容（上限 356/1,782 = 19.98%），是早期文档笔误，已按不可达处理 |
| PR-AUC（AP） | ≥ 两条基线中较好者（实测 0.6498 > 0.6412） | 排序能力必须超过"规则打分"和"逻辑回归" |
| ROC-AUC | 只报告，不设门槛 | 基率 50% 时 ROC-AUC 虚高，容易被误读 |
| Brier | 只报告，并注明漂移 | 训练期基率 13%、验证期 50%，概率系统性偏低是**预期内的**，不作为失败判据 |

门槛是 M1 拟定的初值，M3 实测出基线后定稿；**只允许在验证集上定，绝不碰封存测试集**。

### 4.3 工程质量门槛

- 一条命令重建数据集并写出 `FROZEN.json`，两台机器指纹一致；重跑指纹不变。
- 一条命令跑完质量门（ruff / ruff format / mypy / import-linter / pytest）全绿。
- 测试 ≥ 10 个，覆盖标签边界、哨兵值、时间轴、切分边界、接口 422。
- 所有报告数字都能追溯到一次 mlflow run 或一条命令输出。

## 5. 非目标（明确不做）

1. **不做客户级去重/去重后的"人"级建模**：数据没有客户 ID，同一人可能多次出现，强行去重只能靠特征组合猜，会把误差引进来。口径上以"一次联系尝试"为单位，并在模型卡里说明。
2. **不做因果/增量（uplift）**：只做"排序"，不回答"打了比不打好多少"。数据没有对照组（所有人最终都被打过或没打），做不出因果结论。
3. **不做实时特征与流式打分**：没有在线特征库，服务接收的是整条样本。
4. **不追求 SOTA 分数**：任务书明确模型分数不占分；换来的是可解释性与可维护性（选逻辑回归为主模型）。
5. **不做自动重训调度**：只定义重训触发条件（PSI 超阈值、验证集指标跌破门槛），不实现定时任务。
6. **不做敏感属性的公平性优化**：不做受保护群体的差异化处理，但在模型卡里列出"职业/教育/婚姻"等属性的使用风险，并禁止把模型用于信贷审批等个体决策。
7. **不做前端框架工程化**（本期）：前端最后做静态页，能填表、能显示结果与字段级错误即可。
